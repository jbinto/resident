# Resident

> **AI-generated software disclaimer:** This entire repository—including its code, tests,
> documentation, architecture, and recorded design decisions—was generated by AI coding agents
> working from human requirements and review. It is real, tested software, but it remains
> experimental. Audit it and exercise independent human judgment before trusting it with important
> data or decisions.

Resident is an audio-fingerprint engine for a question that ordinary song-identification tools do
not answer well:

> Where else in my own archive does this passage occur?

It indexes recordings once, keeps their fingerprints in a read-only-friendly store, and compares
recordings without decoding the audio again. It can find a song repeated across radio shows, a
short sample reused years later, two differently encoded copies of the same recording, or one
record audible underneath a voice-over. Its higher-level passage output turns thousands of
fingerprint hits into a small number of inspectable, record-scale observations.

The name comes from DJ culture: a resident is the DJ who knows the room and keeps showing up.

## Why care?

Most fingerprint systems are built around a short unknown clip and a catalogue of clean tracks.
Archives of long-form audio have different problems:

- both sides of the question may be multi-hour recordings;
- the same material may be sped up, pitched, cut, re-cued, or talked over;
- several sources can be audible at once;
- the useful answer is a passage with honest support and holes, not a wall of eight-second hits;
- a missing engine, a missing store, and a genuine no-match result must never look alike;
- matching evidence is not a human identity decision.

Resident is designed around those constraints. It can reproduce the matching behavior of a pinned
Panako 2.1 deployment from imported fingerprint dumps, and it also has a native Rust extraction
lane for building new stores without Java, JNI, or Gaborator.

Resident was developed for **mixmd**, a private archive and tracklisting application for one
curator's roughly 2,600 radio shows, DJ sets, and practice recordings. The engine is intentionally
not coupled to that application: keys are opaque strings, the protocol is JSON Lines, and all
machine output remains proposal-grade evidence.

## The mental model

```text
audio or Panako dumps
        │
        ▼
 fingerprint extraction ──► immutable mmap-backed store
                                      │
                         ┌────────────┴────────────┐
                         ▼                         ▼
                 compatibility matches      passage observations
                 (rows and segments)        (support, holes, quality,
                                              alternates, same-audio hints)
```

There are three layers on purpose:

1. **Prints** are compact facts extracted from audio: `(hash, time, frequency)`.
2. **Matches** reproduce the pinned oracle's offset-line vote and expose its raw evidence.
3. **Passages** join compatible local lines into stable, directional observations while preserving
   support gaps and plausible concurrent alternatives.

Resident never names a song, edits a tracklist, declares an overlay to be speech, or turns a
machine proposal into canon. Those are application and human-review jobs.

## What is unusual here?

### Compare stored recordings directly

`span`, `crosscheck`, `passages`, and `discover` read fingerprints already stored for both sides.
No audio decode or extraction is needed at query time. A store opens by mapping immutable files,
so a long-running process can stay warm while unrelated processes read the same generation.

### Ask once per passage, not once per window

The compatibility API deliberately exposes local match segments. The passage API goes further: it
replays overlapping 12-second/8-second query geometry, deduplicates repeated evidence, stitches
clock-consistent lines, and reports exactly where support exists. A clean alignment can bridge a
short unsupported hole, but the hole remains visible—it is never relabelled as matched audio.

Passage output is also non-exclusive. “B is audible here” does not mean “only B is audible here.”
That distinction is what allows an application to recognize a known underlay without erasing an
unknown voice, drop, or second record on top.

### Compatibility is explicit, not contagious

The matcher preserves a few observable Java/Panako quirks because the fixture oracle requires
them. They are isolated in the compatibility voter. Store ordering, error handling, passage
construction, and the native extractor do not inherit accidental jar behavior.

### Evidence is cheap to revisit

Fingerprints are the expensive durable input. Query profiles and passage rules can evolve over the
same stored prints. Default responses omit granular hit clouds; callers can request evidence for a
specific pair when a human wants to inspect how an answer was formed.

## Quick start

You need the latest stable Rust toolchain and `ffmpeg` for audio extraction. Matching imported
prints does not invoke ffmpeg.

```sh
./check.sh

# Build a store from Panako file-cache dumps.
cargo run --release -- ingest \
  --store ./resident-store \
  --dump-dir fixtures/store-dump

# Prove the matcher against the bundled oracle fixtures.
cargo run --release -- verify fixtures --store ./resident-store

# Keep the store open and serve JSON Lines on stdin/stdout.
cargo run --release -- daemon --store ./resident-store
```

The full gate is `cargo fmt --check`, warning-free Clippy, and all tests. It is intentionally one
script so it can become a CI gate unchanged.

## Useful commands

Extract prints directly. `enroll` is available on the daemon wire when an application deliberately
combines extraction with store publication:

```sh
cargo run --release -- extract ./audio.wav
```

Compare stored audio:

```sh
# One pair, compatibility segments.
cargo run --release -- span \
  --store ./resident-store --a-key show/a --b-key show/b

# One pair, record-grained passage observations.
cargo run --release -- passages \
  --store ./resident-store --a-key show/a --b-key show/b

# Exhaustive fan-out from A. Repeat --target for a bounded target set.
cargo run --release -- discover \
  --store ./resident-store --a-key show/a \
  --target show/b --target show/c
```

`discover` has no top-*k* cutoff. Use repeated `--exclude-key` values for alternate encodings that
the caller has already decided are revisions of A. Until that decision exists, Resident reports a
near-total zero-offset diagonal as `same_audio_candidate` instead of hiding it.

Validate or rebuild the native extraction lane:

```sh
cargo run --release -- validate-extract fixtures --store ./resident-store
cargo run --release -- validate-stream fixtures
cargo run --release -- validate-multiline fixtures --store ./resident-store

cargo run --release -- refingerprint \
  --manifest ./corpus.jsonl --output-dir ./native-dump --jobs 12

cargo run --release -- ab-compare \
  --a-store ./imported-store --b-store ./native-store --probes-dir ./probes
```

`refingerprint` is resumable. It publishes each print file before its metadata completion marker,
records per-resource failures deterministically, and bounds extraction concurrency with `--jobs`.

Repair legacy metadata without re-extracting or rewriting shards:

```sh
cargo run --release -- rehash-identities --store ./resident-store
cargo run --release -- set-durations \
  --store ./resident-store \
  --durations ./durations.jsonl \
  --expected-generation STORE_GENERATION
```

Run `rehash-identities` before banking passage IDs from an old duration-coupled manifest. Then
`set-durations` can publish authoritative durations while proving that shard bytes, endpoint print
hashes, and passage identity inputs did not change.

## Embedding the daemon

The daemon protocol is intentionally small: one JSON request per stdin line, one correlated JSON
response per stdout line, and diagnostics on stderr. Responses may complete out of order because
requests run concurrently.

For example, after starting `resident daemon --store ./resident-store`, write requests like:

```json
{"id":"health-1","verb":"ping"}
{"id":"pair-17","verb":"passages","a_key":"show/a","b_key":"show/b","evidence":false}
{"id":"evidence-9","verb":"span","a_key":"show/a","a_window":[120,180],"b_key":"show/b","evidence":true,"multi_line":true}
```

Every response repeats its request ID and carries either `"ok": true` with the verb payload or
`"ok": false` with a typed error. Do not assume response order.

A robust host should:

- run one long-lived daemon per application process so the store is opened once;
- attach a unique request `id` and correlate every response;
- parse stdout strictly as protocol and drain stderr strictly as logs;
- bound both in-flight work and the waiting queue, returning visible back-pressure;
- use per-verb timeouts—an exhaustive fan-out and a health probe need different budgets;
- distinguish absent binary/store, engine refusal, protocol failure, timeout, process exit,
  overload, and a successful empty result;
- supervise unexpected exits and expose store generation/config in health status;
- mount the store read-only for serving, with one explicit writer responsible for new generations;
- close the child during graceful application shutdown.

The application should normally persist compact passage observations and fetch granular evidence
live for a selected pair. A raw corpus-wide evidence bank is much larger and goes stale whenever
the fingerprints or query profile change.

## Integration invariants

- **Evidence is not identity.** A stable passage ID identifies a machine observation, not a song.
- **The question is directional.** A→B and B→A can differ; missing reverse evidence is not a veto.
- **Matches are non-exclusive.** Concurrent alignments may both be real.
- **Support is narrower than the envelope.** Consumers must not fill reported holes.
- **Scores are not probabilities.** Compare the quality vector and support geometry, not a made-up
  confidence percentage.
- **Same-audio is a candidate relation.** Fingerprints alone cannot distinguish duplicate encoding
  from a deliberate full rebroadcast.
- **Snapshot identity matters.** Bank store generation, config, endpoint content hashes, and passage
  profile with every derived observation; supersede stale observations rather than rewriting them.
- **Failures are not empty answers.** Preserve typed errors across the application boundary.

The complete wire shapes and defaults are in [CONTRACT.md](CONTRACT.md).

## Store model

A store contains an atomic `CURRENT` pointer, immutable generation manifests, and immutable binary
shards. Each shard carries both orders needed by the engine:

- forward postings by resource and time for range scans;
- inverted postings by hash for candidate lookup.

Readers keep their mapped generation while a writer constructs and publishes the next one. Ingest
is idempotent for identical key/content pairs; changed content requires explicit replacement.
Retirement is physical rather than tombstone-forever. The store is derived data: corruption is a
loud refusal followed by rebuild, not an invitation to add a WAL.

The production-scale reference used during development contained about 412 million postings across
2,891 stored resources. Its projected store size is about 21 GiB. The bundled 16-resource fixture
contains 3,208,323 postings and occupies 168 MiB.

## FAQ

### Is this Shazam?

Not really. It uses landmark-style audio fingerprints, but it is optimized for cross-recording
questions inside an owned archive, especially long and messy recordings. It does not ship a song
catalogue or return commercial metadata.

### Does Resident identify songs?

No. It identifies recurring audio evidence between opaque recording keys. An application may use
human-authored metadata from one occurrence to propose a name elsewhere; a human still decides.

### Can it find a song underneath speech or a DJ drop?

It can report the supported underlay alignment without claiming the overlay is absent. It does not
yet classify or separate the residual signal into voice, effects, or another record.

### Why not merge every nearby hit?

Because proximity is not identity. Passage stitching requires both clocks, offset, and speed/pitch
factors to continue coherently. Unsupported holes stay explicit, and strong competing lines remain
separate observations.

### Why are results directional?

Probe geometry, local evidence, target selection, and historical top-*k* truncation can make one
direction differ from the other. Consumers may union banked directions, but must retain provenance.

### What is `same_audio_candidate` for?

Archives often contain MP3/FLAC siblings or revised encodes. Those can otherwise dominate recurrence
results as perfect matches. Resident marks the signal pattern; the caller decides whether the keys
are revisions and can exclude blessed siblings on later discovery jobs.

### Can the store be mounted read-only?

Yes for all query verbs. Keep ingest, retire, enrollment, identity rehash, and duration publication
on a separately controlled writer path.

### Must I use the daemon?

No. The CLI exposes the same core operations and is convenient for maintenance and experiments.
The daemon is the better application boundary when many queries should share one mapped store.

### Is native extraction bit-identical to Panako?

No, and that is not its acceptance target. It preserves the hash/config domain and is evaluated at
print, anchor, and downstream-answer levels. Imported Panako prints remain the compatibility oracle.

### Can I change the matching or passage thresholds later?

Yes. Fingerprints can be re-queried without re-extraction. A change that affects observation
identity must receive a new explicit profile so old and new banks can coexist and be compared.
